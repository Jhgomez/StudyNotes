# Debbuging
Debugging Kotlin corroutines, is a whole process, in that process you have different phases and tools. Your first phase is logs/logging, in backend this is important, you’ll use tools like spring boot or ktor + an aggregator(like Kibana) de aggregator will let you display and filter logs to help you understand exceptions as purely using logs by themselves or collecting them in a file may not be helpful enough when inspecting exceptions in corroutines, in android applications this may not be the best approach as doing something similar will consume network resources and drain battery but if you need to do something similar you will use “datadog” or “sentry”(it recently added this functionality), but a better approach would be using firebase or sentry and use their breadcrumbs functionality which lets you log user interactions with the app just before it crashed. Sentry lets you collect videos or screenshots that will help you understand the state of the app before it crashed, but the most important thing when debbuging corroutines is logs, this is because stack trace when debbuging corroutines is nearly useless in cases where you have a corroutines created inside other corroutines, you could turn on the kotlinx.corroutines.debug system property(doesn’t work on android) to get more helpful info in a stack trace when an exception occurs inside a corroutine.

Usually you would like to log when corroutine starts and ends, it could be useful to set the name of corroutines, you do that when defining a corroutine context, to see these ids in production set the system property mentioned before(its is lightweight)

In backend you should use a custom context to pack user info inside a coroutine context, using the following api `AbstractCoroutineContextElement` in the video you can see an example [at 6m:35s](https://youtu.be/QTX5_JV4TVU?si=rj7wTP3D_XRX0DZm), in the “past” or when you use threads you attach values to the thread using MDC you can use them with corroutines but you have to have a good understanding of both(8m:00s). In backend you can also add the corroutine context info(created with the previously mentioned abstract class) to a log message when you catch an exception in the `CorroutineExceptionHandler` this is done only if you want to customize the logging information as all logging libraries will log exceptions

In android if you don’t set an exception handler, then a default handler is set and this handler will actually throw the exception making it crash, consider adding the viewmodel name in the log declared in the handler

Usually, debbuging will have three phases, first, observe (you use logs here), second, reproduce the error, here, ideally, you’d reproduce it using a unit test if you believe there is a problem with your logic in the domain layer, or use an end to end test, this is usually done by mocking the response from services when making a request to the service. Third and last, now you open the bugger.

## Using Debbuger
Since Kotlin 2 when debugging in AS or IntelliJ, variables are not optimized out by default, letting debug your code better, and in new versions of the IDE debugging with newer versions of the IDE will pause on the same break point across different coroutines but be aware it doesn’t follow a single corroutine execution, for that you should use the “step over” and “run to cursor” options, both guarantees to follow a single corroutine through its execution. You can get this functionallity from "step over", "step out", "runt to cursor", "smart step into", "smart step into launches", basically it remains within the corroutine where stepping started, [this is possible by](https://www.youtube.com/watch?v=3vaAVtnrzAM) using saving the corroutine id and filtering the corroutines with it

FYI, if you need to wait for  corroutine to complete its execution you can call them inside them corroutineScope function or call join or joinAll on the job returned by it’s constructor(launch)

More advanced tools is the “parallel stack” for corroutines in debugger, it shows the stack of corroutines and the relationship between them. The stack of corroutines in the debugger is actually pretty good and way more useful than their just pure stack trace in the console when an exception occurs. Also “debug agent” is a little harder to use but can help a lot in big systems with lots of corroutines, don’t use it in production, it doesn’t work in android runtime(android jvm) but you can use it in some unit tests for some android components.

## [Performance](https://www.youtube.com/watch?v=QTX5_JV4TVU&t=1551s)
For measuring backend systems you have tools like “micrometer”, it collects all measurements of the app and sends it to an appropriate collector like Prometheus + grafana, with those tools the metrics related to coroutines that you’d keep an eye on are, cpu usage, thread pool usage, and to some degree, also disk and network IO. Also in general you should set custom metrics like queue lengths, cache hits and misses, open connections, execution time for specific functions. Also Business metrics, active users, conversion rate, specific events.

### Meassuring
In backend, you should measure buffer, in spring boot with Prometheus you’d use the “updates.buffer.count” in the gauge in the registry to create an atomic Integer that you can increment in an on each operator and then de decrement in another on each, also measure flow observers. Meassuring in Android might not be as important as in the backend as we don’t really know what the user is doing with our app but you can use tools like “android vitals”, firebase performance monitoring, “jankstats” library to count the number of missed frames, to do some performance meassurement.

## Optimizations
* **BlockHound**: it will help you by throwing an exception whenever you block a dispatcher that should not be blocked, for example according to marcin, in Android changing context of an coroutine with `withContext` to change to IO dispatcher to fetch something from the backend is a mistake because this is not a blocking function while in the backend when you do things like writing to disk should be done in the IO dispatcher, don’t use it production though, just in debug mode, be aware in big projects you could get false positives from libraries/dependencies.

* **Indepedent Dispatchers**: In the backend you should create independent dispatchers with custom limits with `Dispatchers.IO.limitedParallelism(20)` also the number of concurrent requests made to outer services should be limited using a semaphore or something like resilience 4j `rateLimiter`

## Cancelation
For cancellation using structured concurrency, let’s say you have a supend function that contains a corroutine scope and starts some corroutines inside this scope, in this example we will see 4 scenarios. First, you can also call other suspending functions from this scope. Second, you can call the “launch” function to start a corroutine inside this scope. Third, you could use a different scope to start a corroutine this will create a corroutine bounded to a different scope other than the one referenced at the beginning. Fourth, also do what is considered an anti-pattern, which is starting a corroutine that is bounded to the scope mentioned at the beginning but passing a custom job object in a `launch` corroutine builder like launch(Job()), it is an antipattern because this job is not related to the scope that started the corroutine. Regarding cancellation, when the parent scope is cancelled, suspending functions called within the scope that are currently running are cancelled, also other running corroutines bounded to that scope(child corroutines), but the last two cases we mentioned are not cancelled, corroutines started using another scope, or corroutines following the anti-pattern mentioned, actually if you want the corroutine not be canceled then use a different scope, as you can see, those are not cancelled.

## [A Practical Example](https://www.youtube.com/watch?v=nKCsIHWircA&t=1290s)
Here we learn about the `kotlinx-coroutines-test` library, we were introduced the `runTest` corroutine builder. That corroutine builder by default creates a `TestScopea` which enables us to run supend functions or creat other corroutines, this test scope will have a special dispatcher, the default dispatcher is `TestDispatcher` which at the same time uses a `TestCorroutineScheduler`, be aware all dispatchers have to reference the same instance of that scheduler, this is important to know. Also the test dispatcher has two implementations, `StandardTestDispatcher` or `UnconfinedTestDispatcher`, by default the dispatcher all corroutines created in the test scope will be ran using the `StandardTestDispatcher` if you don't specify a different dispatcher then this is the dispatcher all corroutines will use, the catch with this type is that you have to advance time manually with functions like `runCurrent()`, `advanceTimeBy(millis)`, `advanceUntilIdle`, this happens because this dispatcher queues new corroutines. `UnconfinedTestDispatcher` actually execute corroutines eagerly, that is why is usually used to mock the main dispatcher, also is usually used for corroutines that collect flows, but it is also said that it doesn't emulate real concurrency. Be aware the main dispatcher is not accessible from a test/virtual runtime, so if you want to use it implicitly when testing a viewmodel's ViewmodelSscope since this scope uses the main dispatacher under the hood you have tu use the function `Dispatchers.setMain(Dispatcher)`, also make sure to reset the main dispatcher with `Dispatcher.resetMain()`, this is usually done inside a try/catch but doing this in all of the test you write may not be convenient and to solve this you'd use things like JUnit4, which will let you define test rules in which you can set the main dispatcher by overrinding the starting method fo your custom rule and calling `resetMain` from the overriden "finished" function of your custom rule. they show us the `runTest` corroutine builder which creates a default corroutine scope called  to test a viewmodel that launches corroutines using its viewmodel scope,, be aware all delays using the `delay` function are ignored, this happens only within the test dispatcher, if you switch context to another dispatcher like IO, they will actually happen
