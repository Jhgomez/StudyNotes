# Debbuging
Debugging Kotlin corroutines, is a whole process, in that process you have different phases and tools. Your first phase is logs/logging, in backend this is important, you’ll use tools like spring boot or ktor + an aggregator(like Kibana) de aggregator will let you display and filter logs to help you understand exceptions as purely using logs by themselves or collecting them in a file may not be helpful enough when inspecting exceptions in corroutines, in android applications this may not be the best approach as doing something similar will consume network resources and drain battery but if you need to do something similar you will use “datadog” or “sentry”(it recently added this functionality), but a better approach would be using firebase or sentry and use their breadcrumbs functionality which lets you log user interactions with the app just before it crashed. Sentry lets you collect videos or screenshots that will help you understand the state of the app before it crashed, but the most important thing when debbuging corroutines is logs, this is because stack trace when debbuging corroutines is nearly useless in cases where you have a corroutines created inside other corroutines, you could turn on the kotlinx.corroutines.debug system property(doesn’t work on android) to get more helpful info in a stack trace when an exception occurs inside a corroutine.

Usually you would like to log when corroutine starts and ends, it could be useful to set the name of corroutines, you do that when defining a corroutine context, to see these ids in production set the system property mentioned before(its is lightweight)

In backend you should use a custom context to pack user info inside a coroutine context, using the following api `AbstractCoroutineContextElement` in the video you can see an example [at 6m:35s](https://youtu.be/QTX5_JV4TVU?si=rj7wTP3D_XRX0DZm), in the “past” or when you use threads you attach values to the thread using MDC you can use them with corroutines but you have to have a good understanding of both(8m:00s). In backend you can also add the corroutine context info(created with the previously mentioned abstract class) to a log message when you catch an exception in the `CorroutineExceptionHandler` this is done only if you want to customize the logging information as all logging libraries will log exceptions

In android if you don’t set an exception handler, then a default handler is set and this handler will actually throw the exception making it crash, consider adding the viewmodel name in the log declared in the handler

Usually, debbuging will have three phases, first, observe (you use logs here), second, reproduce the error, here, ideally, you’d reproduce it using a unit test if you believe there is a problem with your logic in the domain layer, or use an end to end test, this is usually done by mocking the response from services when making a request to the service. Third and last, now you open the bugger.

## Using Debbuger
Since Kotlin 2 when debugging in AS or IntelliJ, variables are not optimized out by default, letting debug your code better, and in new versions of the IDE debugging with newer versions of the IDE will pause on the same break point across different coroutines but be aware it doesn’t follow a single corroutine execution, for that you should use the “step over” and “run to cursor” options, both guarantees to follow a single corroutine through its execution

FYI, if you need to wait for  corroutine to complete its execution you can call them inside them corroutineScope function or call join or joinAll on the job returned by it’s constructor(launch)

More advanced tools is the “parallel stack” for corroutines in debugger, it shows the stack of corroutines and the relationship between them. The stack of corroutines in the debugger is actually pretty good and way more useful than their just pure stack trace in the console when an exception occurs. Also “debug agent” is a little harder to use but can help a lot in big systems with lots of corroutines, don’t use it in production, it doesn’t work in android runtime(android jvm) but you can use it in some unit tests for some android components
